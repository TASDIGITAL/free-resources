# tas-creative-playbook

The Cloudflare Worker `free-resources`, which serves two sites from one script:

| Hostname | Site |
|---|---|
| `creative.tas-digital.ai` | VSL landing page at `/`, Creative Strategy Playbook at `/library` |
| `resources.tas-digital.ai` | The full client resource library |

Resource content comes from Airtable at request time, so adding or editing a
resource needs no deploy. Only code changes do.

## Deploying

Push to `main`. Cloudflare Workers Builds watches this repo and deploys.
There is no Cloudflare step to perform and nothing to upload by hand.

## src/worker.js is the deployed artifact, not a build output

This Worker used to be generated by a `build.py` that inlined and minified two
page templates. That is deliberately **not** how this repo works.

In October 2026 the Worker was rebuilt from an on-disk source tree that had
drifted months behind what was actually live. The rebuild was correct about the
one field it added and silently reverted five shipped changes: the VSL video,
the lead-magnet booking calendar, the copy fixes, the resource counts and the
New badge. Nobody noticed until the video was reported broken three weeks later.

So this repo holds exactly one thing: the file that is deployed. What is in
`src/worker.js` is what runs. There is no second copy that can fall behind it.

Edit it in place and push.

## Secrets and bindings

`AIRTABLE_TOKEN` and `GHL_TOKEN` are Worker secrets set in the Cloudflare
dashboard. They are never committed, and `wrangler deploy` preserves them.

## Verifying a deploy

A successful build is not a correct page. After deploying, load
`creative.tas-digital.ai` and check the VSL iframe mounts, and `/library` and
check the booking links resolve to the lead-magnet calendar
(`…discovery-callpzjkrl`), not the Website/Ads one (`…callyetoev`).
